# Architecture RFC — Termu-inator v1

Status: M1 contract-freeze candidate, 2026-08-24.

This RFC is the **Normative target** for v1. Statements below describe the
required architecture unless an implementation-status note says otherwise.

## Current alpha gaps

The compact `tbp-mcp-v1` path already composes one typed service authority with
session ownership, capability negotiation, refs, verified actions,
permissions/confirmations, durable artifacts/traces, bounded Developer queries,
and the optional loopback shared view. Both legacy browser engines use the same
adapter contract for observation and the eight typed action kinds.

The preserved `tbp` CLI and 148-tool `tbp-mcp` server have not yet been routed
through that service. Real legacy adapters also lack authoritative tab/popup and
dialog event streams, project-scoped completed-download bytes, and pre-follow
redirect/DNS interception. Device crash recovery, long soak, SSH round trips,
and clean-install verification remain release gates rather than local claims.

## Intent

Termu-inator is an AI-first browser runtime for Termux/Android, not an anti-bot
bypass product. It provides a small remote tool surface, stable observations,
verified actions, explicit backend capabilities, content-addressed artifacts,
and human approval boundaries while preserving the existing v0.x commands
during migration.

Chromium is the default backend because the S22U baseline met all warm latency
budgets and used substantially less aggregate RSS. Firefox remains an explicitly
selected compatibility backend. The runtime never switches backend
automatically because profiles, cookies, page state, and capabilities can
differ.

## Runtime Boundaries

```text
Hermes / Codex / CLI
         |
         | MCP stdio or local CLI
         v
compact transport adapters ---- legacy v0.x adapters
         |
         v
Termu-inator service layer
  session | observe | act | permissions | artifacts | trace
         |
         v
BrowserBackend protocol
  Chromium CDP adapter | Firefox native adapter | fake test adapter
         |
         v
Termux browser + Xvfb + openbox
```

Transport modules parse and serialize only. Policy, idempotency, session state,
backend selection, verification, and artifact handling live in the service
layer so CLI and MCP cannot diverge. The MCP host transport establishes the
owner scope; caller-supplied `project_id` cannot grant access to another owner.

## Session and Profile Model

The system uses project-scoped persistent profiles and one active browser
session per daemon.

- One daemon permits a single active session. A second start returns
  `session_busy`; it never silently takes over an existing browser.
- The MCP API requires `project_id`. CLI derives it from the canonical current
  working directory when omitted and displays the resolved value.
- Project-scoped persistent profiles are stored below a SHA-256-derived project
  directory and split again by backend and profile-schema revision. A canonical
  layout is `projects/<digest>/profiles/<backend>/v1/profile`; service policy,
  approval, idempotency, artifact, and trace state is stored outside the
  browser-writable profile. The plain project path or label is not used as a
  filesystem path.
- Session identifiers, page identifiers, document epochs, element refs, and
  confirmation identifiers are opaque values generated by the service.
- User sign-in takeover pauses all agent page, artifact, trace, and Developer
  reads as well as actions. Only redacted control-plane status remains. Resume
  requires an explicit local host or CLI action, rotates the document epoch,
  and requires a fresh observation.

## BrowserBackend Contract

The backend protocol owns start, stop, cached status, navigate, observe, act,
wait, tabs, screenshots, downloads, and approved Developer queries. Every
session start returns a revisioned `CapabilitySet`. Each capability carries a
fidelity state (`supported`, `emulated`, `partial`, `unsupported`, or `broken`),
reason, limits, dependencies, and last probe time. Observations bind the exact
capability revision. Unsupported operations return `unsupported_capability`
and must never report a synthetic success.

Chromium uses CDP where available. Firefox uses a browser-owned, loopback-only
WebDriver BiDi session for navigation and JavaScript-backed observation, with
the existing DevTools/clipboard evaluator retained only when the Remote Agent
is unavailable. X11 still owns native input and window capture. Firefox status
is a control-plane cache read with a freshness timestamp rather than two
synchronous evaluations. The backend updates that cache after navigation and
every action.

## Observe–Act–Verify Flow

1. `browser_observe` records session, page, document epoch, mutation counter,
   normalized interactive elements, optional screenshot artifact, and backend
   capabilities.
2. The service issues opaque refs. The agent does not invent selectors.
3. `browser_act` supplies the observed page revision, ref, idempotency key, and
   typed action parameters.
4. The service checks transport ownership, origin permission,
   revision/ref/capability freshness, server-derived risk, and any server-held
   approval before calling the backend.
5. The backend executes once. The service performs action-specific
   verification and returns an `ActionResult` with before/after revisions.

Document, tab, or origin changes invalidate all refs. A DOM-only mutation may
revalidate an unchanged fingerprint for R0/R1 operations. R2 and higher require
a new observation.

## Persistence and Remote Data

- Permission decisions, profiles, traces, and artifacts are separated per
  transport owner, project, backend where applicable, and schema revision.
- Artifacts use `artifact://sha256/<digest>` identifiers and bounded 512 KiB
  reads. Transport responses do not expose arbitrary device paths.
- The MVP shared view is a default-OFF static read-only server over the same
  service authority: current cached screenshot, redacted URL/title/tab,
  value-free pending permission/confirmation summaries, and up to 20 recent
  secret-free traces. It stops page output during confidential takeover and
  cannot approve or execute actions.
- The implemented viewer accepts only literal loopback binding and uses
  `no-store`, restrictive CSP, Host validation, and anti-embedding headers.
  Direct Tailnet binding is deferred; a future implementation would be a
  separate host operation protected by encrypted tailnet transport and a
  high-entropy bearer authorization header.

## Compatibility and Delivery

The internal namespace moves to `termuinator`, while the distribution and
commands remain `termux-browser-pilot`, `tbp`, and `tbp-mcp` throughout v0.x.
The target product default is the compact MCP server. In the current alpha
checkout, `tbp-mcp` still starts the 148-tool compatibility server and
`tbp-mcp-v1` explicitly starts the compact server. The compatibility server may
move behind an explicit `--legacy` launch mode through v0.2, but it is never
used by the provided Hermes/Codex compact configurations.

The target compatibility layer delegates legacy read, navigation, click,
input, and screenshot commands to the same service methods. That delegation and
the default-disable migration for sensitive legacy operations are not complete;
until then, the legacy server is a trusted-local compatibility surface and
cannot inherit compact-mode safety claims.

## Failure and Recovery

- Socket, PID, lock, browser, and profile ownership are probed before reuse.
- Crash recovery produces a new document epoch and invalidates all refs and
  approvals.
- Action idempotency uses a durable journal. The service persists
  `reserved`/`waiting_confirmation` before `dispatched`, then one terminal
  result. A different payload under the same key is `idempotency_conflict`; an
  interrupted dispatched action is `outcome_unknown` and is never automatically
  repeated.
- Every public failure has a stable error code and optional private diagnostic
  identifier. Raw exception strings do not become the public API.
- The target HTTP(S) policy checks resolved addresses before connection and
  every redirect. The current legacy adapter checks canonical origin permission
  before the initial navigation and quarantines an unexpected resulting origin
  only after backend return; pre-follow redirect and DNS-rebinding prevention
  remain open.
- External websites are non-gating. Deterministic local fixtures are the
  release authority.
